# HoopUp — ภาพรวมระบบและสิ่งที่ยังไม่ได้ส่งมอบ

วันที่ 28 ตุลาคม 2569 · เทียบเอกสารแนวคิดเดิมกับ source และผลตรวจในเครื่องวันนี้

**แอปจากงาน 4 คนครอบคลุมแกนหานัดและเติมทีม ยังไม่ครอบคลุมทุกระบบที่เคยคุยกัน** การเลื่อนฟีเจอร์ในใบงานเป็นขอบเขตของรอบพัฒนา ไม่ถือว่าผู้ใช้ยกเลิกแนวคิดนั้น หรืออนุมัติรายละเอียดทุกข้อแล้ว

เอกสารนี้เป็นการสรุปสถานะและข้อเสนอจัดลำดับ ยังไม่ได้เปลี่ยนใบงานเดิมหรือสั่งเริ่มพัฒนารอบใหม่

## ฟีดที่เคยคุยกัน

- บันทึก 25 ต.ค. เวลา 18:39–18:47 มีการคุยเรื่อง social/activity feed: ข้อความ/รูป ไลก์ คอมเมนต์ ติดตามสนามหรือก๊วน และเรียงรายการล่าสุด รายละเอียดเหล่านี้เป็นข้อเสนอในการสนทนา ไม่ใช่ specification ที่ผู้ใช้อนุมัติทั้งหมด
- Frontend brief 26 ต.ค. ใช้ feed รายการนัดเป็น baseline และแยกโพสต์ทั่วไปไว้รอบต่อไป งาน 4 คนจึงทำ feed แบบนี้
- ปัจจุบันมี `FeedPage` สำหรับค้นหานัด แต่ยังไม่มีระบบโพสต์รูป ไลก์ คอมเมนต์ หรือติดตาม และ SQL ปัจจุบันไม่มีตารางรองรับ social feed เหล่านี้
- ถ้าจะทำ social feed ต้องกำหนดหน้าหรือแท็บที่จะเข้าใช้ ชนิดโพสต์และผู้เห็นโพสต์ พร้อมเพิ่ม data model/API/สิทธิ์/upload/การดูแลเนื้อหาตามขอบเขตที่เลือก ไม่ควรถือว่าการ์ดนัดเท่ากับส่ง social feed เสร็จแล้ว

## สถานะรายระบบ

| ระบบ | สิ่งที่มีในรอบนี้ | ส่วนที่ยังค้าง / สถานะข้อเสนอเดิม |
|---|---|---|
| ฟีดหานัด | หน้าและการ์ดนัด ตัวกรองชื่อ/สนาม/รูปแบบ/ระดับ ทดลอง demo ได้ | ตัวกรองต้องทำงานกับข้อมูลมากกว่าหน้าแรก; ช่วงวันเวลาตาม brief ยังต้องเติม/ตรวจ และยังไม่ยืนยันการใช้ backend จริง |
| ฟีดกิจกรรม/โพสต์ | ยังไม่มี implementation | โพสต์ข้อความ/รูป ไลก์ คอมเมนต์ ติดตาม และ pagination เป็นขอบเขตเสนอให้เลือกสำหรับรอบใหม่ |
| สร้างนัด/เข้าทีม | Demo สร้าง ตอนนี้/กำหนดเวลา ขอร่วม อนุมัติ ถอน ปิดรับ จบ/ยกเลิก | แก้ account-state defects และตรวจ Auth/RLS/concurrency บน development backend จริง |
| นัดของฉัน/แชท | มีหน้าและ service; สองแท็บแลกข้อความได้เมื่อ refresh | เปลี่ยนบัญชีต้องล้างข้อมูลเดิม; connected chat ต้องอ่านชุดข้อความล่าสุด; ยังไม่มี Realtime/push |
| บัญชี/โปรไฟล์ | แบบฟอร์มชื่อ ระดับ ตำแหน่งและส่วนสูง; mock users; Supabase adapter | Login route/mode, reactive identity และ logout มี defect; สมัครบัญชี/ขั้นตอนเริ่มต้นสำหรับผู้ใช้จริงและอัปโหลดรูปยังไม่ได้ส่งเป็น flow ครบ |
| รายการสนาม | มี catalogue พร้อมข้อมูลสนามสมมติและทางเข้าดูนัด/สร้างนัด | ต้องเตรียมข้อมูลสนามจริงและตรวจรายละเอียด ไม่ถือว่าข้อมูลตัวอย่างผ่านการยืนยันสถานที่ |
| สนามใกล้ฉัน/แผนที่ | Schema เก็บพิกัด มี optional PostGIS migration; บาง card มี helper คำนวณระยะทาง | ยังไม่มีเส้นทางขอตำแหน่งผู้ใช้ ค้นรัศมี/viewport และแผนที่ใช้งานครบ; ต้องเลือก tile/provider และแหล่งข้อมูลสนาม |
| แจ้งเตือนสำคัญ | ยังไม่มีระบบ notification ที่ส่งให้ผู้รับ | ผลอนุมัติ สมาชิกเข้าหรือถอน แก้เวลา/สนาม ยกเลิก; เสนอเริ่มกล่องแจ้งเตือนในแอปก่อนเลือก push |
| ฉันว่าง/แจ้งห้องใกล้ฉัน | มีในภาพอ้างอิง; โปรไฟล์ปัจจุบันแสดงเป็นรายการรอพัฒนา | ต้องออกแบบอายุสถานะว่าง พื้นที่/รัศมี ความสนใจ ความยินยอม และกติกาไม่ส่งเตือนซ้ำก่อนทำ matching |
| สนามประจำ/ติดตามสนาม | มีในภาพและแนวคิด; ยังไม่มีระบบบันทึกจริง | ความสัมพันธ์ผู้ใช้–สนาม และการใช้กับ feed/notification ยังต้องออกแบบ |
| รีวิว/รายงานสภาพสนาม | อยู่ในแนวคิดฉบับรวม ยังไม่มี implementation | รีวิว/รูป สภาพล่าสุดพร้อมเวลารายงานและการจัดการข้อมูลเก่า; ข้อมูลไม่ทราบต้องแสดงตามจริง |
| ก๊วน/เพื่อน/ติดตาม/นัดประจำ | เคยคุยเป็นส่วนต่อยอด | ยังไม่ได้เลือกกติกาหรือพัฒนา; หนึ่งนัดหนึ่งทีมปัจจุบันยังไม่ใช่ระบบก๊วนถาวร |
| รีพอร์ต/บล็อก | มี UI กับ service/RPC ตั้งต้น | ยังไม่ตรวจแบบ connected ครบ; ยังไม่มีหน้าผู้ดูแลจัดการรายงาน และนโยบายสมาชิกเดิมที่บล็อกกันยังต้องตกลง |
| ประวัติ/อันดับ/แชร์ผลงาน | เคยระดมแนวคิด ยังไม่เลือกแบบสุดท้าย | ผู้ใช้เคยให้ feedback ว่า photo/passport basketball cards ยังไม่โดนใจ จึงไม่ยกกลับมาเป็นข้อกำหนดอัตโนมัติ; ไม่มีหลักฐานว่ารับทำทุกแนวเป็น scope เดียวกัน |

คำว่า “มี” ในตารางหมายถึงพบ implementation หรือทดลองได้ตามที่ระบุ ไม่ใช่ผ่าน production acceptance ทุกกรณี ดูผลตรวจจริงใน [Independent review](mvp_tasks_2026-10-28/audit_2026-10-28/REVIEW.md)

## ลำดับถัดไปที่เสนอให้พิจารณา

1. **ทำฐานที่ทดสอบได้ให้เรียบร้อย:** แก้ auth/account-state และ QA ตาม review แล้วเชื่อม development backend จริง เพื่อใช้ร่วมทุกระบบ
2. **ขยายงานผลิตภัณฑ์เป็นขอบเขตชัดเจน:** เลือก social feed รุ่นพื้นฐาน, สนามใกล้เคียง/แผนที่ และการแจ้งเตือนเป็นงานรอบถัดไปที่แยก interface กันได้; ขั้นนี้สามารถออกแบบคู่ขนานกับการแก้ฐาน แต่ไม่อ้างว่าเชื่อมใช้งานจริงแล้ว
3. **เพิ่มการกลับมาใช้งาน:** สนามประจำ/สถานะว่าง/ติดตาม และรีวิวสภาพสนามตามความต้องการที่เลือก ก่อนเพิ่มก๊วนถาวร/อันดับหรือโมดูลอื่นที่ยังไม่ตกลง

เกณฑ์แยกความพร้อม: demo ในเครื่อง → backend development จริง → ทดลองกับผู้เล่น/สนามจริง → ผู้ใช้ตรวจรับ แต่ละขั้นต้องมีหลักฐานของตัวเอง และไม่กำหนดวันเสร็จโดยยังไม่มีประมาณงาน

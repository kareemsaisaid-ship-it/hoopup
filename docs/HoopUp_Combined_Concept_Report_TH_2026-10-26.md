# HoopUp — รายงานแนวคิดฉบับรวม

**ระบบค้นหาเพื่อนร่วมทีมและข้อมูลสนามบาสสาธารณะ**  
วันที่จัดทำ: 26 ตุลาคม 2569  
สถานะ: ฉบับรวมสำหรับอ่านและพิจารณาขอบเขต ยังไม่ใช่ข้อกำหนดที่ทีมอนุมัติทั้งหมด

## 1. ภาพรวมของแนวคิด

HoopUp เป็นแอปที่ช่วยให้คนอยากเล่นบาสหาคนเล่นด้วย เลือกสนาม และนัดหมายกันได้ในที่เดียว ผู้ใช้สามารถเปิดห้องเพื่อเติมคนให้ทีม หรือเข้าร่วมห้องของคนอื่น โดยเห็นสนาม เวลา จำนวนคนที่ขาด ระดับและบรรยากาศการเล่นก่อนตัดสินใจ

แนวคิดฉบับนี้รวม **ห้องหาคนเติมทีม** จากเอกสารของทีม กับ **ข้อมูลสนามและการช่วยให้คนใหม่เข้ากลุ่มได้ง่ายขึ้น** จากบันทึกแนวคิดเดิม ส่วนการกำหนดเวลาใช้ข้อสรุปล่าสุดของผู้ใช้ว่า **“เล่นตอนนี้” เป็นเพียงตัวเลือกเวลาเริ่ม ไม่ต้องแยกเป็นอีกโหมด**

คำอธิบายผลิตภัณฑ์หนึ่งประโยค:

> **อยากเล่นบาส เปิดห้องหรือหาห้องที่เข้ากัน เลือกสนามและเวลา แล้วนัดไปเล่นด้วยกัน**

ข้อความสื่อสารที่เสนอคือ “มาคนเดียว ก็หาเพื่อนเล่นได้” โดยเป็นเป้าหมายของบริการ ไม่ใช่การรับประกันว่าจะมีคนเข้าร่วมหรือได้ลงเล่นทุกครั้ง

## 2. ที่มาของส่วนที่นำมารวม

| ที่มา | ส่วนที่นำมาใช้ในรายงาน |
|---|---|
| เอกสาร HoopUp ของทีม | หนึ่งห้องต่อหนึ่งทีม, รูปแบบ 3x3/5x5, ตำแหน่งผู้เล่น, ระดับการเล่น, การเข้าร่วม, แชท, แผนที่และการแจ้งเตือน |
| แนวคิดสนามสาธารณะเดิม | รายละเอียดสนาม, รีวิวประสบการณ์, รายงานสภาพล่าสุดพร้อมเวลา และข้อจำกัดว่าการนัดไม่ใช่การจองสนาม |
| แนวคิดคอมมูนิตี้เดิม | บอกสไตล์การเล่นและการรับมือใหม่ให้ชัด มีผู้จัดหรือคนติดต่อที่คนใหม่หาตัวได้เมื่อมาถึง |
| ข้อสรุปของผู้ใช้ในแชตนี้ | ใช้ห้องแบบเดียว เลือกเวลาเริ่มเป็นตอนนี้หรือวันและเวลาที่ต้องการ |
| ข้อเสนอเพิ่มเติมในรายงาน | นับเพื่อนที่ไม่มีบัญชีได้, ตำแหน่งยืดหยุ่น, แยกห้องเต็มจากห้องจบ และแบ่งขอบเขตพัฒนาเป็นระยะ |

ข้อเสนอเพิ่มเติมและการจัดลำดับพัฒนายังต้องให้ผู้ใช้และทีมพิจารณา ไม่ถือว่าได้รับอนุมัติเพียงเพราะรวมไว้ในรายงาน

## 3. ปัญหาที่ต้องการแก้และกลุ่มผู้ใช้

ปัญหาหลักมีสองฝั่งที่เชื่อมกัน คือ **คนอยากเล่นแต่ยังไม่มีเพื่อนร่วมทีม** กับ **ทีมที่มีคนอยู่แล้วแต่ยังขาดผู้เล่น** ข้อมูลสนามช่วยประกอบการเลือกว่าจะไปเล่นที่ใด ส่วนข้อมูลสไตล์และผู้จัดช่วยให้คนใหม่รู้ว่าจะเข้าหาใคร

| กลุ่มผู้ใช้ | ปัญหาหรือความต้องการ | สิ่งที่ HoopUp เสนอให้ |
|---|---|---|
| คนมาคนเดียวหรือเพิ่งย้ายพื้นที่ | ยังไม่รู้จักก๊วน ไม่แน่ใจว่ากลุ่มไหนรับคนใหม่ | ค้นหาห้องที่รับคนและระบุบรรยากาศการเล่น |
| กลุ่มเพื่อนที่คนไม่ครบ | มีเพื่อนบางส่วนแล้ว ต้องการเติมอีกไม่กี่คน | เปิดห้องโดยระบุคนที่มีอยู่และจำนวนที่ขาด |
| ผู้จัดหรือหัวหน้าก๊วน | ต้องบอกสนาม เวลา และตอบคำถามคนเข้าร่วมซ้ำ | รวมรายละเอียดนัด รายชื่อ และช่องทางติดต่อไว้ในห้อง |
| ผู้เล่นที่กำลังเลือกสนาม | ยังไม่ทราบรายละเอียดหรือสภาพสนามล่าสุด | อ่านข้อมูลสนาม รีวิว และรายงานที่ระบุเวลา |

เอกสารทีมวางกลุ่มเป้าหมายเริ่มต้นเป็นผู้เล่นขาจรอายุประมาณ 15–35 ปี แต่รายงานนี้ยังไม่มีผลสำรวจยืนยันว่าช่วงอายุใดมีความต้องการสูงสุด ปัญหาและแรงจูงใจจึงควรตรวจด้วยผู้เล่นจริงก่อนกำหนดขอบเขตสุดท้าย

## 4. แกนการใช้งาน: ห้องหาผู้เล่น

### 4.1 หนึ่งห้องแทนหนึ่งทีมที่จะไปเล่น

ห้องใช้รวบรวมผู้เล่นฝั่งเดียวให้ครบตามจำนวนที่ตั้งไว้ เช่น 3 คนสำหรับทีมที่จะเล่น 3x3 หรือ 5 คนสำหรับทีมที่จะเล่น 5x5 ไม่ได้หมายความว่าภายในห้องมีสองทีมพร้อมแข่งกันแล้ว

เมื่อทีมครบ สมาชิกจึงนัดไปสนามและจัดการเล่นกับคนที่สนามตามสถานการณ์จริง ทีมอื่นไม่ต้องใช้แอปด้วย และการเข้าห้องไม่ทำให้สมาชิกได้สิทธิ์จองสนามหรือข้ามคิวของคนที่อยู่ก่อน

### 4.2 รายละเอียดที่ผู้สร้างห้องระบุ

| รายการ | ตัวอย่างหรือแนวทาง |
|---|---|
| ชื่อห้อง | บาสเย็นสวนลุม รับมือใหม่ |
| สนาม | เลือกสนามจากรายการหรือแผนที่ |
| เวลาเริ่ม | ตอนนี้ / วันนี้ 19:00 / เลือกวันและเวลา |
| รูปแบบทีม | 3x3 หรือ 5x5 |
| คนที่มีอยู่แล้ว | รวมผู้สร้างและเพื่อนที่มาด้วย |
| คนที่ยังต้องการ | แสดงจากจำนวนทีมลบจำนวนคนที่ยืนยันแล้ว |
| ระดับการเล่น | ชิล ๆ / เล่นประจำ / จริงจัง |
| สไตล์และการรับคนใหม่ | เล่นออกกำลังกาย รับมือใหม่ หรือเล่นค่อนข้างจริงจัง |
| ตำแหน่งที่ต้องการ | ระบุตำแหน่ง หรือเลือกตำแหน่งไหนก็ได้ |
| วิธีเข้าร่วม | เข้าได้เลย หรือรอผู้สร้างอนุมัติ |
| ผู้ติดต่อและจุดนัดพบ | ถึงแล้วติดต่อใคร เจอตรงไหน |
| หมายเหตุ | มีลูกบาสแล้ว เล่นถึงประมาณสามทุ่ม |

**ข้อสรุปเรื่องเวลา:** ห้องทุกห้องใช้กระบวนการเดียวกัน ต่างกันที่เวลาเริ่ม การแสดงหมวด “ใกล้เริ่ม” หรือ “นัดถัดไป” บนหน้าแรกทำได้จากเวลาของห้อง โดยไม่ต้องสร้างระบบห้องสองชนิดและไม่ต้องเปลี่ยนโหมดเมื่อถึงเวลา

**ข้อเสนอเรื่องตำแหน่ง:** ใช้ตำแหน่งช่วยค้นหาคนที่เหมาะ แต่เปิดให้ผู้จัดเลือกแบบยืดหยุ่นได้ ไม่จำเป็นต้องบังคับให้ทุกทีมมี PG, SG, SF, PF และ C อย่างละคน

### 4.3 เพื่อนที่ไม่ได้ใช้แอป

ข้อเสนอฉบับรวมคือให้ผู้สร้างระบุจำนวนเพื่อนที่มาด้วยได้ โดยไม่ต้องให้ทุกคนสมัครบัญชีก่อน เช่น ผู้สร้าง 1 คน มีเพื่อนมาด้วย 2 คน และเปิดรับเพิ่ม 2 คน รวมเป็นทีม 5 คน

จำนวนคนที่มีอยู่ต้องรวมผู้สร้างแล้วเพื่อไม่ให้นับซ้ำ หากภายหลังเพื่อนคนเดิมเข้าร่วมผ่านบัญชี ต้องแทนที่ที่นั่งเดิม ไม่เพิ่มเป็นอีกคนหนึ่ง รายชื่อเพื่อนที่ผู้สร้างเพิ่มเองไม่ควรถูกแสดงเหมือนบัญชีที่ยืนยันการเข้าร่วมด้วยตนเอง

## 5. เส้นทางใช้งานตั้งแต่ค้นหาจนไปเล่น

**ฝั่งผู้สร้างห้อง:** เลือกสนามและเวลา → ระบุคนที่มีและคนที่ขาด → ตั้งสไตล์การเล่นและวิธีเข้าร่วม → เปิดรับคน → คุยรายละเอียด → นัดพบและไปเล่น

**ฝั่งคนหาทีม:** เลือกพื้นที่และช่วงเวลาที่สะดวก → ดูห้องที่ยังรับคน → อ่านรายละเอียดทีมและสนาม → เข้าร่วมหรือส่งคำขอ → ได้รับการยืนยัน → คุยจุดนัดพบ → ไปเล่น

ตัวอย่างสมมติ: เอมีเพื่อนรวมตัวเอง 3 คน อยากเล่น 5x5 วันนี้เวลา 19:00 จึงเปิดห้องรับเพิ่ม 2 คน ระบุว่าเล่นประจำแต่รับคนใหม่ และเลือกตำแหน่งไหนก็ได้ บีมาคนเดียว อ่านรายละเอียดแล้วกดเข้าร่วม ส่วนซีเข้ามาเป็นคนที่ห้า ห้องจึงแสดงว่าเต็ม ทุกคนยังคุยกันได้ว่าเจอกันตรงไหน หากซีถอนตัว ห้องสามารถเปิดรับคนแทนได้ตามกติกาที่ทีมกำหนด

ถ้าเอต้องการเล่นตอนนี้ก็เลือกเวลา “ตอนนี้” ในห้องแบบเดียวกัน กระบวนการสร้างและเข้าร่วมยังเหมือนเดิม

## 6. กติกาห้องที่เสนอให้ใช้

ส่วนนี้เป็นข้อเสนอเพื่อปิดช่องว่างของเอกสารเดิม ยังต้องให้ทีมยืนยันรายละเอียด

| สถานการณ์ | พฤติกรรมที่เสนอ |
|---|---|
| ยังมีที่ว่าง | เปิดรับคนและแสดงจำนวนที่ขาด |
| ผู้เล่นส่งคำขอแบบรออนุมัติ | แสดงว่ารออนุมัติ ยังไม่ถือว่าได้ที่นั่ง |
| มีคนกดเข้าร่วมที่นั่งสุดท้ายพร้อมกัน | ยืนยันได้ตามจำนวนที่เหลือ ผู้ที่ไม่ได้ที่นั่งต้องได้รับข้อความชัดเจน |
| คนครบแล้ว | แสดงสถานะเต็มและหยุดรับเพิ่ม แต่ยังเปิดดูรายละเอียดและใช้แชทได้ |
| สมาชิกถอนตัว | คืนที่นั่งและแจ้งผู้จัด หากยังเปิดรับอยู่ให้กลับไปแสดงว่าขาดคน |
| ถึงเวลาเริ่มแต่คนยังไม่ครบ | ให้ผู้จัดเลือกว่าจะรับต่อหรือปิดรับ ไม่ต้องเปลี่ยนชนิดห้อง |
| เปลี่ยนสนามหรือเวลาหลังมีคนร่วม | แจ้งสมาชิกให้เห็นการเปลี่ยนแปลงชัดเจน และให้ถอนตัวได้ |
| ผู้จัดยกเลิก | แสดงสถานะยกเลิกและแจ้งสมาชิก |
| เล่นจบหรือหมดช่วงรับคน | ปิดรับและเก็บเป็นประวัติตามระยะเวลาที่จะตกลงกัน |

ยังต้องตกลงว่าใครปิดห้องได้ อายุห้องและการเก็บแชทนานเท่าไร รวมถึงผู้สร้างถอนตัวแล้วต้องยกเลิกหรือส่งต่อผู้จัดได้หรือไม่ รายงานนี้ยังไม่ตั้งตัวเลขแทนทีม

**ตำแหน่งที่ตั้งและเช็คอิน:** ข้อเสนอคือให้เลือกสนามและสร้างห้องได้โดยไม่บังคับว่าอยู่สนามแล้ว ใช้ตำแหน่งปัจจุบันเมื่อผู้ใช้ยินยอมเพื่อช่วยค้นหาสนามใกล้ตัว และให้เลือกพื้นที่เองได้ ส่วนการเช็คอินว่า “มาถึงแล้ว” เป็นอีกความสามารถหนึ่งที่ต้องพิจารณาตามประโยชน์จริง การเลือกเวลา “ตอนนี้” ไม่ใช่เหตุผลเพียงพอที่จะบังคับ GPS

## 7. ข้อมูลสนามและการต้อนรับคนใหม่

### 7.1 ข้อมูลสนามที่ช่วยตัดสินใจก่อนออกเดินทาง

หน้าสนามควรมีชื่อ ตำแหน่ง รูป และข้อมูลที่ตรวจสอบได้ เช่น ในร่มหรือกลางแจ้ง ประเภทพื้น จำนวนห่วง ไฟกลางคืน และเวลาเปิด–ปิด รายการที่ยังไม่ทราบให้ระบุว่ายังไม่มีข้อมูล

รีวิวควรบอกช่วงเวลาที่ผู้รีวิวไปและสิ่งที่พบ เช่น บรรยากาศการเล่นหรือสภาพพื้น โดยแยกจากข้อมูลพื้นฐานที่ทีมดูแล ไม่สรุปว่าสนามนั้นมีผู้เล่นระดับใดตลอดเวลาเพียงเพราะมีคนรีวิวครั้งเดียว

รายงานสภาพล่าสุด เช่น พื้นเปียก สนามปิด หรือไฟดับ ต้องมีเวลารายงานและแหล่งที่มา ข้อมูลเก่าหรือขัดกันต้องแสดงตามจริง ไม่มีรายงานไม่ได้หมายความว่าสนามเปิดและพร้อมเล่น ส่วนจำนวนทีมที่รอเป็นเพียงรายงานจากผู้ใช้ ไม่ใช่คิวทางการของสนาม

### 7.2 ลดความไม่แน่ใจของคนเข้าร่วมครั้งแรก

ห้องควรระบุให้ชัดว่ารับมือใหม่หรือไม่ เล่นสไตล์ไหน และเมื่อถึงสนามให้ติดต่อใคร เช่น “ผู้จัดใส่เสื้อแดง เจอที่ม้านั่งข้างทางเข้า” เพื่อให้คนใหม่มีจุดเริ่มต้นในการเข้ากลุ่ม

แนวคิดหน้าก๊วนประจำและการติดตามก๊วนสามารถต่อยอดภายหลังได้ ระยะแรกใช้ข้อมูลผู้จัดและรายละเอียดห้องรองรับความต้องการนี้ก่อน โดยยังต้องทดสอบว่าช่วยให้คนไปพบกันได้ง่ายขึ้นจริงหรือไม่

## 8. ขอบเขตเวอร์ชันแรกที่เสนอ

เป้าหมายของเวอร์ชันแรกคือทดลองให้ครบว่า **มีคนเปิดห้อง มีคนเข้าร่วม และสมาชิกไปพบกันจริง** การมีผู้สมัครบัญชีหรือกดเข้าห้องเพียงอย่างเดียวยังไม่ยืนยันผลส่วนนี้

| ทำในเวอร์ชันทดลอง | ขอบเขตที่เสนอ |
|---|---|
| บัญชีและโปรไฟล์ | ชื่อ รูป ระดับที่ผู้ใช้ระบุเอง ตำแหน่งหลัก/รองหรือเล่นได้ทุกตำแหน่ง; ส่วนสูงไม่บังคับ |
| รายการและแผนที่สนาม | เริ่มเฉพาะสนามนำร่องที่ทีมเข้าถึงและมีข้อมูลตั้งต้น |
| ห้องและการค้นหา | สร้างห้อง เลือกเวลา ระบุคนที่มี กรองสนาม/ช่วงเวลา/ระดับ และดูจำนวนที่ขาด |
| การเข้าร่วม | เข้าได้เลยหรือรออนุมัติ ถอนตัว และป้องกันจำนวนเกิน |
| การนัดพบ | รายละเอียดผู้ติดต่อ แชทในห้อง และการแจ้งเตือนสำคัญ |
| การดูแลผู้ใช้ | รีพอร์ต บล็อก และกำหนดผลของการบล็อกต่อการมองเห็นและการเข้าร่วมให้ชัด |

การแจ้งเตือนสำคัญเริ่มจากผลอนุมัติ สมาชิกเข้าหรือถอนตัว และการเปลี่ยนหรือยกเลิกนัด ส่วน “ฉันว่าง อยากเล่น” และการส่งแจ้งเตือนหาคนที่ตำแหน่งตรงโดยอัตโนมัติให้เป็นระยะถัดไป เมื่อทราบว่าการค้นหาและเข้าร่วมพื้นฐานยังติดขัดตรงไหน

รายงานสภาพสนามและรีวิวฉบับเต็มไม่จำเป็นต้องเปิดรับทั้งระบบตั้งแต่วันแรก ทีมสามารถเตรียมข้อมูลพื้นฐานสนามนำร่องก่อน แล้วเพิ่มการรายงานและการดูแลข้อมูลเมื่อมีผู้รับผิดชอบชัดเจน

## 9. ส่วนต่อยอดและสิ่งที่พักไว้

| กลุ่ม | แนวคิด |
|---|---|
| ต่อยอดการหาคน | สถานะว่าง การแจ้งเตือนตามความสนใจสนาม ตำแหน่งและสไตล์การเล่น |
| ต่อยอดคอมมูนิตี้ | ติดตามผู้จัดหรือก๊วน นัดประจำ เพื่อน และความคิดเห็นหลังเข้าร่วม |
| ต่อยอดข้อมูลสนาม | รีวิว รายงานพร้อมรูป การติดตามสนาม และข้อมูลอากาศที่แยกจากสภาพสนามจริง |
| แนวคิดที่ยังไม่เลือก | ประวัติสนามที่เคยเล่นหรือพาสปอร์ตสนาม ต้องตรวจว่าผู้ใช้ต้องการบันทึกจริงก่อน |
| ระยะหลังเมื่อมีเหตุผลรองรับ | ความน่าเชื่อถือจากประวัติการเข้าร่วม การจัดทัวร์นาเมนต์ และรูปแบบรายได้ |

ระบบคะแนนความน่าเชื่อถือยังต้องมีกติกาเรื่องหลักฐาน การยกเลิกที่มีเหตุผล และการโต้แย้ง ไม่ควรถือว่าผู้ใช้ไม่มาตามนัดเพียงเพราะไม่มีการเช็คอิน

การแบ่งทีมอัตโนมัติ การจัดคิวชนะอยู่ต่อของทั้งสนาม กล้องวิเคราะห์ท่าชู้ต และโมดูลฝึกส่วนตัวพักไว้นอกขอบเขตฉบับนี้ การรวมแนวคิดครั้งนี้เลือกเฉพาะส่วนที่ช่วยการหาเพื่อนร่วมทีม เลือกสนาม และนัดพบกัน

## 10. แนวทางเริ่มทดลองและประเมินผล

เสนอให้เริ่มพื้นที่เล็ก เช่น สนามที่ทีมเข้าถึงจริง 1–3 แห่ง และชวนผู้จัดที่ยินดีรับคนใหม่มาลองก่อน จำนวนนี้เป็นข้อเสนอสำหรับนำร่อง ไม่ใช่จำนวนสนามหรือผู้ใช้ที่ติดต่อสำเร็จแล้ว

ขั้นแรกให้ผู้เล่นลองต้นแบบด้วยสถานการณ์ “มากันสามคน อยากได้อีกสองคน” และ “มาคนเดียว อยากหาเกมเย็นนี้” เพื่อตรวจว่าหาข้อมูล สร้างห้อง และเข้าร่วมได้เข้าใจตรงกันหรือไม่ จากนั้นจึงทดลองนัดจริงและเก็บผล โดยใช้การประสานงานผ่านแชตตามปกติเป็นข้อมูลเปรียบเทียบในสถานการณ์ที่ใกล้กัน

| คำถามประเมิน | ข้อมูลที่ควรเก็บ |
|---|---|
| สร้างห้องและเข้าร่วมเข้าใจง่ายหรือไม่ | งานที่ทำสำเร็จ เวลาที่ใช้ จุดที่ต้องให้ผู้ทดสอบขอความช่วยเหลือ |
| ห้องช่วยเติมคนได้หรือไม่ | จำนวนห้องที่เปิดรับและห้องที่ได้คนครบ พร้อมแยกห้องยกเลิก |
| ได้คนครบเร็วเพียงใด | เวลาจากเปิดรับถึงครบ โดยรายงานห้องที่ยังไม่ครบแยกไว้ด้วย |
| คนเข้าร่วมไปจริงหรือไม่ | การยืนยันหลังนัดจากผู้เข้าร่วมและผู้จัด พร้อมระบุกรณีข้อมูลไม่ตรงกันหรือไม่ตอบ |
| คนใหม่หากลุ่มเจอหรือไม่ | ปัญหาเมื่อถึงสนาม ความชัดเจนของจุดนัดพบ และความคิดเห็นหลังใช้ |
| ผู้จัดอยากกลับมาใช้หรือไม่ | การเปิดห้องซ้ำและเหตุผลที่ใช้ต่อหรือกลับไปใช้แชต |

ยังไม่กำหนดเป้าหมายเชิงตัวเลข จำนวนตัวอย่าง ระยะเวลาทดลอง หรือกำหนดส่ง เพราะยังไม่มีข้อมูลที่ทีมยืนยัน หากนำไปใช้เป็นโครงงาน ต้องตกลงวัตถุประสงค์ วิธีเปรียบเทียบ และเกณฑ์ประเมินกับอาจารย์อีกครั้ง รายงานนี้ไม่รับรองว่าขอบเขตผ่านอนุมัติทางวิชาการแล้ว

## 11. แนวทางเทคโนโลยีจากเอกสารทีม

เอกสารทีมเสนอ React Native และ Expo ด้วย TypeScript สำหรับมือถือ, Supabase สำหรับข้อมูลและการอัปเดต, PostGIS สำหรับงานเชิงพื้นที่, Expo Notifications สำหรับแจ้งเตือน และ LINE/Google/Apple สำหรับล็อกอิน

รายการดังกล่าวเป็นเทคโนโลยีที่ทีมเสนอ ไม่ใช่ผลตรวจความพร้อมใช้งาน ข้อจำกัด ค่าใช้จ่าย หรือความเข้ากันได้ของรุ่นปัจจุบันในรายงานนี้ การเลือกช่องทางล็อกอินที่จะทำก่อนควรอิงกลุ่มทดลองและความพร้อมของทีม

เอกสารต้นทางระบุว่ามีโค้ด Expo และ Supabase แล้ว แต่การจัดทำรายงานครั้งนี้ไม่ได้ตรวจ repository ฐานข้อมูล หรือรันแอป จึงยังยืนยันไม่ได้ว่าส่วนใดทำงานจริงแล้ว

## 12. เรื่องที่ต้องตกลงก่อนพัฒนา

1. รับแกน “ห้องหาคนเป็นส่วนหลัก ข้อมูลสนามช่วยตัดสินใจ” ตามฉบับรวมนี้หรือไม่ และเวอร์ชันแรกต้องมีข้อมูลสนามลึกแค่ไหน
2. ยืนยันกติกานับเพื่อนที่ไม่มีบัญชี การใช้ตำแหน่งแบบยืดหยุ่น และการอนุมัติที่นั่ง
3. กำหนดอายุห้อง การสิ้นสุดนัด การถอนตัว และกรณีผู้จัดออกจากห้อง
4. ตกลงว่าการเช็คอินจำเป็นต่อปัญหาใด หากจะมี ต้องแยกจากตัวเลือกเวลาเริ่ม
5. เลือกสนามนำร่อง ผู้ดูแลข้อมูล ผู้จัดที่ร่วมทดลอง และผู้รับเรื่องรายงานปัญหา
6. กำหนดแพลตฟอร์ม จำนวนสมาชิกทีม เวลาที่มี และเกณฑ์ทดลองก่อนประเมินกำหนดส่ง

**ผลลัพธ์ที่ฉบับรวมนี้มุ่งให้เกิด:** ผู้เล่นเห็นว่ามีใครเปิดรับคน ไปสนามไหน เวลาใด เล่นสไตล์ใด และต้องติดต่อใคร ขณะที่ผู้จัดเห็นจำนวนคนที่มีและยังขาดอยู่ โดยใช้ห้องรูปแบบเดียวกันตลอดเส้นทาง

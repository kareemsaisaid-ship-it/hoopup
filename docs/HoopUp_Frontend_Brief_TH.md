# HoopUp — Brief ส่งต่อทีม Frontend

วันที่: 26 ตุลาคม 2569 · ฉบับ 0.1  
วัตถุประสงค์: ใช้จัดหน้า ออกแบบ interaction และพัฒนา frontend จากแกนเดียวกัน

**เอกสารเชื่อม backend เพิ่มเติม:** [API / RPC v0.1](backend/API_TH.md) และ [TypeScript contract](backend/frontend-contract.ts) มีชื่อคำสั่งและรูปแบบข้อมูลที่เสนอไว้แล้ว SQL core ผ่านการทดสอบในเครื่องด้วย Auth จำลอง แต่ยังไม่มี Cloud endpoint ที่ deploy สำหรับแอปจริง

> **Core: เปิดนัดเล่นบาส แล้วให้คนเข้ามาเติมทีม**
>
> หนึ่งนัดบอกให้ครบว่า **ใครจัด · สนามไหน · เวลาใด · มีใครมา · ขาดอีกกี่คน**

เอกสารนี้รวมแนวคิดทีมกับการคุยล่าสุด ข้อสรุปที่ผู้ใช้ยืนยันชัดคือ **“เล่นตอนนี้” เป็นตัวเลือกเวลาเริ่มของนัดเดียวกัน ไม่แยกโหมด** ส่วนรายละเอียด UX และกติกาที่เพิ่มไว้เป็น baseline สำหรับเริ่มทำต้นแบบ ต้องให้ทีมตรวจร่วมกันก่อนเชื่อมระบบจริง เอกสารนี้ไม่ได้ยืนยัน API หรือ schema ฐานข้อมูลที่มีอยู่

## 1. ภาพของผลิตภัณฑ์

HoopUp ช่วยสองฝั่งมาเจอกัน: คนอยากเล่นแต่ยังไม่มีทีม และทีมที่มีคนแล้วแต่ยังขาดผู้เล่น ผู้ใช้เปิดนัดหรือหานัดที่เข้ากัน แล้วคุยรายละเอียดเพื่อไปพบกันที่สนาม

- **หนึ่งนัด/หนึ่งห้อง = หนึ่งทีม** จำนวน 3 หรือ 5 คน รวมผู้จัด ไม่ใช่ผู้เล่นสองทีมรวมกัน 6 หรือ 10 คน
- ใช้คำว่า **“นัด”** บนหน้าจอให้สม่ำเสมอ คำว่า “ห้อง” ในเอกสารเดิมหมายถึงหน่วยเดียวกัน
- มีนัดรูปแบบเดียว เลือกเริ่มตอนนี้หรือกำหนดวันและเวลา
- นัดเป็นข้อมูลกลาง ฟีด แผนที่ นัดของฉัน และแชทอ้างถึงนัดเดียวกัน
- การเข้าร่วมนัดเป็นการรวมทีมไปเล่น ไม่ใช่การจองสนามหรือสิทธิ์ข้ามคิวในสนามสาธารณะ

**ฟีดในฉบับนี้คือรายการนัดเล่นบาส** ยังไม่รวมโพสต์ทั่วไป ไลก์ คอมเมนต์ หรือฟีดวิดีโอ

## 2. สิ่งที่ frontend ต้องทำให้ผู้ใช้ทำสำเร็จ

**คนหาทีม:** เปิดฟีด → กรองพื้นที่/เวลา → ดูนัด → เข้าร่วมหรือขอเข้าร่วม → ได้รับการยืนยัน → คุยจุดนัดพบ

**ผู้จัด:** สร้างนัด → เลือกสนามและเวลา → ใส่คนที่มีและคนที่ขาด → เปิดรับ → ดูสมาชิก/จัดการคำขอ → คุยจุดนัดพบ → จบนัดหรือยกเลิก

ตัวอย่าง: ผู้จัดมากับเพื่อนอีก 2 คน รวมเป็น 3 คน ต้องการทีม 5 คน จึงเปิดรับเพิ่ม 2 คน คนมาคนเดียวเข้าร่วมได้ เมื่อครบแล้วนัดยังเปิดอ่านและคุยกันได้ หากมีคนถอนและยังเปิดรับอยู่จึงกลับมารับเพิ่ม

## 3. โครงสร้างเมนูที่เสนอ

| เมนูหลัก | หน้าที่ |
|---|---|
| หานัด | ฟีดนัดพร้อมตัวกรองและปุ่มสร้างนัด |
| สนาม | รายการ/แผนที่สนาม และนัดที่เกี่ยวข้อง |
| นัดของฉัน | นัดที่จัด นัดที่เข้าร่วม และคำขอที่รออนุมัติ |
| โปรไฟล์ | ข้อมูลและการแก้ไขโปรไฟล์ |

หน้ารายละเอียดนัด สร้าง/แก้ไขนัด รายละเอียดสนาม แชท และรายการคำขอ เปิดต่อจากเมนูเหล่านี้ ไม่ต้องมีแท็บแยกทุกหน้า

## 4. หน้าจอและพฤติกรรม

### F01 — ฟีดหานัด

- แสดงการ์ดนัดที่ยังเปิดรับเป็นรายการหลัก พร้อมปุ่ม **“สร้างนัด”** ที่หาเจอง่าย
- ตัวกรองเริ่มต้น: พื้นที่หรือสนาม, วัน/ช่วงเวลา, 3x3/5x5 และระดับการเล่น
- อาจเพิ่มตำแหน่งที่รับภายหลังหากตัวกรองพื้นฐานพอใช้งานแล้ว
- การ์ดแสดงชื่อ สนาม วันเวลา รูปแบบ ระดับ คนที่มี/จำนวนเต็ม คนที่ขาด และวิธีเข้าร่วม
- หากมีข้อมูลระยะทางจึงแสดง; หากไม่มีตำแหน่งให้เลือกพื้นที่เองและยังใช้งานต่อได้
- ลำดับเริ่มต้นที่เสนอ: ใกล้เวลาเริ่มก่อน; การเรียงตามระยะทางเป็นอีกตัวเลือก ไม่อ้างเวลาเดินทางจากระยะทางเส้นตรง
- แตะการ์ดไป F03 ซึ่งเป็นรายละเอียดนัดเดียวกันกับที่เปิดจากแผนที่หรือนัดของฉัน

ตัวอย่างการ์ด — ข้อมูลสมมติ:

```text
บาสเย็น รับคนเพิ่ม
สนามตัวอย่าง A · วันนี้ 19:00
5x5 · เล่นประจำ · รับคนใหม่
มี 3/5 คน · ขาดอีก 2 คน
ตำแหน่งไหนก็ได้ · เข้าได้เลย
[ดูนัด]
```

### F02 — สร้าง/แก้ไขนัด

| ฟิลด์ | ข้อกำหนดของต้นแบบ |
|---|---|
| ชื่อนัด | จำเป็น |
| สนาม | จำเป็น เลือกจากสนามตั้งต้น |
| เวลาเริ่ม | จำเป็น เลือก “ตอนนี้” หรือ “เลือกวันและเวลา” ในฟอร์มเดียวกัน |
| รูปแบบ | 3x3 หรือ 5x5; ใช้กำหนดจำนวนเต็มของทีม |
| เพื่อนที่มาด้วย | จำนวนคนเพิ่มเติมนอกจากผู้จัด; ป้ายต้องบอกชัดว่าไม่รวมตัวเอง |
| ระดับ | ชิล ๆ / เล่นประจำ / จริงจัง |
| รับมือใหม่ | เปิด/ปิด |
| ตำแหน่งที่รับ | ค่าเริ่มต้น “ตำแหน่งไหนก็ได้”; เลือกระบุเพิ่มได้ |
| วิธีเข้าร่วม | เข้าได้เลย / ผู้จัดอนุมัติ |
| จุดนัดพบ | ข้อความที่ช่วยให้หากลุ่มเจอ |
| หมายเหตุ | ไม่บังคับ เช่น มีลูกบาสแล้ว |

แสดงสรุปสด เช่น **“คุณ 1 คน + เพื่อน 2 คน = มีแล้ว 3 คน · รับเพิ่ม 2 คน”**

- เพื่อนที่มาด้วยต้องเป็นจำนวนเต็ม ไม่ติดลบ และรวมผู้จัดแล้วไม่เกินจำนวนทีม
- เปลี่ยน 5x5 เป็น 3x3 ต้องตรวจจำนวนคนใหม่; ถ้าเกินให้แก้ก่อนบันทึก ไม่ลบสมาชิกเอง
- “ตอนนี้” บันทึกเป็นวันเวลาจริง ไม่สร้างชนิดนัดอีกแบบ ไม่แปลงโหมดอัตโนมัติ
- เวลาที่เลือกเองต้องไม่เป็นอดีตเมื่อยืนยันสร้างนัด; การแสดง “ตอนนี้” ในรายการไม่ควรค้างตลอดอายุของนัด
- ต้นแบบใช้เวลาไทยและตัวอย่างเวลาแบบ `วันนี้ 19:00`; ข้อมูลวันเวลาควรมีเขตเวลาชัดเจนเมื่อเชื่อม backend
- ไม่บังคับ GPS เพื่อสร้างนัดใน baseline นี้; ข้อกำหนดเช็คอินยังต้องตัดสินแยก
- ระหว่างบันทึกแสดง loading และป้องกันกดซ้ำ; ล้มเหลวต้องรักษาข้อมูลฟอร์มให้แก้หรือส่งใหม่ได้
- แก้สนาม/เวลาหลังมีคนร่วม ต้องมีข้อความเตือนว่ากระทบสมาชิก; การแจ้งสมาชิกจริงเป็นงานเชื่อม backend

### F03 — รายละเอียดนัด

เรียงข้อมูลสำคัญก่อน: **สนามและเวลา → มี/ขาดกี่คน → ระดับและบรรยากาศ → ปุ่มเข้าร่วม** จากนั้นจึงแสดงผู้จัด สมาชิก จุดนัดพบ ตำแหน่งที่รับ และหมายเหตุ

- แสดงชื่อและข้อมูลติดต่อผ่านผู้จัด/แชทในแอป ไม่ต้องเปิดเบอร์โทรต่อสาธารณะ
- สมาชิกที่มีบัญชีแสดงชื่อ/รูป; เพื่อนที่ผู้จัดเพิ่มเองแสดงเป็นกลุ่ม เช่น “เพื่อนของผู้จัด 2 คน” ไม่สร้างบัญชีปลอม
- ตำแหน่งเป็นความต้องการของทีม เปิดให้เลือกแบบยืดหยุ่น ไม่บังคับ PG/SG/SF/PF/C อย่างละคน
- ระดับเป็นข้อมูลที่ผู้ใช้ระบุเอง ไม่แสดงเหมือนผ่านการประเมินฝีมืออัตโนมัติ
- มีทางไปหน้าสนาม และเมนูรายงานปัญหา/บล็อกตามบทบาทและกติกาที่จะเชื่อมจริง
- รายละเอียดควรบอกว่าการเข้าร่วมไม่ใช่การจองสนาม โดยไม่ให้ผู้ใช้ต้องผ่านหน้าข้อตกลงซ้ำทุกครั้ง

| ผู้ดู/สถานะ | ปุ่มหลักหรือการทำงาน |
|---|---|
| ยังไม่เข้าร่วม + นัดเปิดรับ | “เข้าร่วม” หรือ “ขอเข้าร่วม” ตามวิธีรับคน |
| รออนุมัติ | “รอผู้จัดอนุมัติ” พร้อมทางยกเลิกคำขอ |
| อนุมัติแล้ว/เข้าร่วมแล้ว | “แชทในนัด” และทางถอนตัว |
| นัดเต็ม + ยังไม่ได้ร่วม | “คนครบแล้ว” ไม่มีปุ่มยืนยันเข้าร่วมที่ใช้งานได้ |
| ผู้จัด | จัดการนัด คำขอ สมาชิก แชท ปิดรับ/เปิดรับต่อ จบนัด และยกเลิก |
| ปิดรับแล้ว | แสดงสถานะปิดรับ; สมาชิกเดิมยังดูรายละเอียดและแชทได้ |
| ยกเลิก/จบแล้ว | แสดงผลชัดเจน ไม่เปิดรับสมาชิกใหม่ |

### F04 — คำขอเข้าร่วมและสมาชิก

- ผู้จัดเห็นผู้ขอเข้าร่วมพร้อมชื่อ ระดับ และตำแหน่งที่ระบุ
- มีปุ่มอนุมัติ/ไม่อนุมัติ พร้อม loading และผลลัพธ์; คำขอที่รอไม่ถือว่าครองที่นั่ง
- หากที่นั่งหมดก่อนอนุมัติ แสดง “นัดเต็มแล้ว” และอัปเดตรายการ ไม่แสดงอนุมัติสำเร็จ
- คำขอซ้ำหรือคำขอที่ถูกยกเลิกแล้วต้องไม่เพิ่มสมาชิกซ้ำ
- ต้นแบบต้องมีตัวอย่างทั้งไม่มีคำขอ รออนุมัติ อนุมัติสำเร็จ และที่นั่งหมดระหว่างทำรายการ

### F05 — แชทในนัด

- baseline ให้ผู้จัดและสมาชิกที่ยืนยันแล้วใช้แชทได้ ผู้ขอที่ยังรออนุมัติยังอ่านแชทไม่ได้
- แสดงหัวข้อสนาม เวลา และจุดนัดพบให้เปิดดูง่าย
- รองรับสถานะส่งอยู่ ส่งสำเร็จ และส่งไม่สำเร็จพร้อมลองใหม่
- นัดเต็มแล้วยังคุยได้ ไม่ปิดแชทเพียงเพราะคนครบ
- เมื่อถอนตัว จบนัด หรือยกเลิก ต้องรองรับการจำกัดสิทธิ์/อ่านอย่างเดียวตามค่าที่บริการส่งกลับ; ระยะเวลาเก็บแชทยังไม่กำหนด

### F06 — สนามและรายละเอียดสนาม

- ดูรายการหรือแผนที่สนาม แล้วเปิดรายละเอียดสนามเดียวกันได้
- แสดงชื่อ ตำแหน่ง รูป และข้อมูลพื้นฐานที่มี เช่น พื้น ไฟ เวลาเปิด–ปิด
- ข้อมูลที่ไม่มีแสดง “ยังไม่มีข้อมูล”; ไม่มีรายงานล่าสุดไม่เท่ากับสนามพร้อมเล่น
- แสดงนัดของสนามนั้น พร้อมปุ่ม “สร้างนัดที่สนามนี้” ซึ่งเติมสนามใน F02 ให้แล้ว
- หากแผนที่หรือตำแหน่งใช้ไม่ได้ ต้องยังเลือกสนามจากรายการได้
- ส่วนรีวิวและรายงานสภาพสนามแบบเต็มเป็นระยะต่อไป ไม่สร้างข้อมูลสภาพปัจจุบันขึ้นเองเพื่อเติมหน้าจอ

### F07 — นัดของฉัน

- แยกดู “กำลังจะไป”, “รออนุมัติ”, “ฉันเป็นผู้จัด” และ “ที่ผ่านมา” ได้
- เปิดไป F03 ด้วย ID นัดเดิม ไม่ทำสำเนาข้อมูลแยกอีกชุด
- ถอนตัวหรือผู้จัดยกเลิกแล้ว สถานะในหน้านี้และหน้าอื่นต้องสอดคล้องกัน

### F08 — โปรไฟล์และการเข้าสู่ระบบ

- โปรไฟล์: ชื่อ รูป ระดับ ตำแหน่งหลัก/รอง หรือเล่นได้ทุกตำแหน่ง; ส่วนสูงไม่บังคับ
- ทำหน้าจอเข้าสู่ระบบและกรอกโปรไฟล์ครั้งแรกเท่าที่ต้องใช้ใน flow
- การสร้าง/เข้าร่วม/แชทต้องมีผู้ใช้ที่เข้าสู่ระบบแล้ว; กลับมาทำรายการเดิมต่อได้หลังเข้าสู่ระบบ
- เอกสารทีมเสนอ LINE/Google/Apple แต่ช่องทางที่เปิดจริงยังต้องตรวจร่วมกับ backend; ต้นแบบใช้ mock login ได้และระบุให้ชัด
- รองรับเมนูรายงานปัญหาและบล็อก พร้อมผลสำเร็จ/ผิดพลาด ไม่ใช้ข้อมูล mock แทนการบันทึกจริงเมื่อเชื่อมระบบแล้ว

## 5. กติกากลางที่ทุกหน้าต้องใช้ตรงกัน

```text
คนที่มี = ผู้จัด 1 คน + เพื่อนที่ผู้จัดเพิ่ม + สมาชิกที่ยืนยันแล้ว
คนที่ขาด = จำนวนเต็มของทีม − คนที่มี
คำขอรออนุมัติไม่รวมในคนที่มี
```

ผู้ใช้หนึ่งบัญชีต้องไม่ถูกนับซ้ำ หากเพื่อนที่ผู้จัดเพิ่มเข้ามาสมัครและร่วมด้วยบัญชีภายหลัง ต้องจัดการแทนที่ที่นั่งเดิม; วิธีระบุตัวเพื่อนคนเดิมยังเป็นเรื่องที่ต้องตกลง ไม่ให้ frontend เดาว่าเป็นคนเดียวกันจากชื่อ

### สถานะที่ UI ต้องรองรับ

นี่คือสถานะเพื่อออกแบบหน้าจอ ยังไม่ใช่ชื่อ enum ของฐานข้อมูลที่ยืนยันแล้ว

| สถานะ | ความหมาย |
|---|---|
| เปิดรับ | ยังรับคนและมีที่ว่าง |
| เต็ม | จำนวนครบ หยุดรับเพิ่ม แต่ไม่ได้แปลว่าจบนัด |
| ปิดรับ | ผู้จัดหยุดรับ แม้ยังอาจมีที่ว่าง |
| จบแล้ว | นัดสิ้นสุด ไม่รับเพิ่ม |
| ยกเลิก | ไม่ดำเนินนัดต่อ ไม่รับเพิ่ม |

- ถ้ามีคนถอนจากนัดเต็ม ให้กลับไปเปิดรับเฉพาะเมื่อนัดยังไม่ปิดรับ ไม่จบ และไม่ยกเลิก
- ถึงเวลาเริ่มไม่ใช่เหตุให้จบหรือยกเลิกนัดอัตโนมัติ
- ต้นแบบให้ผู้จัดกดจบนัด/ยกเลิก พร้อมยืนยันการกระทำ; อายุห้องอัตโนมัติและการส่งต่อผู้จัดยังเป็น TBD
- frontend แสดงผลและส่งคำขอ ส่วนการตัดสินที่นั่งสุดท้าย สิทธิ์ และผลอนุมัติจริงต้องยึด backend ไม่ใช้เพียงตัวเลขคงเหลือในเครื่อง

## 6. ข้อมูลที่หน้าจอต้องการ

เป็นรายการสำหรับทำ mock และคุย data contract ชื่อ field เป็นเพียงตัวอย่าง ไม่ใช่ API endpoint หรือ schema ที่ตกลงแล้ว

| กลุ่มข้อมูล | ข้อมูลหลัก |
|---|---|
| นัด | `id`, ชื่อ, `hostId`, `courtId`, วันเวลาเริ่ม, รูปแบบ, จำนวนเต็ม, จำนวนเพื่อน, ระดับ, รับมือใหม่, ตำแหน่งที่รับ, วิธีรับคน, จุดนัดพบ, หมายเหตุ, สถานะ/การเปิดรับ |
| ผู้ใช้ | `id`, ชื่อ, รูป, ระดับที่ระบุเอง, ตำแหน่งหลัก/รอง |
| การเข้าร่วม | `sessionId`, `userId`, สถานะคำขอ/สมาชิก, สิทธิ์ที่ทำได้ |
| สนาม | `id`, ชื่อ, พิกัดถ้ามี, รูป, รายละเอียดที่ทราบและเวลาตรวจข้อมูลถ้ามี |
| แชท | `id`, `sessionId`, ผู้ส่ง, ข้อความ, เวลา, สถานะการส่ง |
| ข้อมูลเสริมสำหรับ UI | จำนวนคนที่มี/ขาด, ระยะทางถ้ามี, ปุ่มที่ผู้ใช้ปัจจุบันทำได้ |

แนะนำให้หน้าจออ่านข้อมูลผ่าน service/hook กลางที่สลับ mock กับบริการจริงได้ ฟีด แผนที่ และนัดของฉันอ้าง ID เดียวกัน หลังเปลี่ยนสมาชิกให้ refresh/invalidate ข้อมูลนัดที่เกี่ยวข้อง ไม่เก็บจำนวนคนแบบอิสระคนละหน้า

## 7. สถานะหน้าจอที่ต้องออกแบบ

| สถานการณ์ | สิ่งที่ต้องเห็น/ทำได้ |
|---|---|
| กำลังโหลด | loading/skeleton ที่ไม่ทำให้กดรายการซ้ำ |
| ไม่มีนัด | ข้อความชัดเจน พร้อมสร้างนัดหรือปรับตัวกรอง |
| ไม่พบตามตัวกรอง | ปรับหรือล้างตัวกรองได้ |
| ไม่อนุญาตตำแหน่ง | เลือกพื้นที่/สนามเองได้ |
| โหลดผิดพลาด/เน็ตหลุด | ข้อความและลองใหม่; ไม่แสดงรายการค้างเหมือนข้อมูลสด |
| กำลังส่งคำขอ | ป้องกันกดซ้ำและแสดงสถานะรอ |
| ที่นั่งเต็มระหว่างเข้าร่วม | แจ้งว่านัดเต็มแล้วและอัปเดตจำนวน ไม่เพิ่มสมาชิกในเครื่องเอง |
| เปิดนัดที่ถูกลบหรือไม่มีสิทธิ์ | ข้อความเข้าใจง่ายและทางกลับรายการ |
| ถอนตัว/ยกเลิกนัด | ยืนยันก่อนทำ และอัปเดตหน้าที่เกี่ยวข้องหลังสำเร็จ |

ข้อความทั้งหมดใช้ภาษาไทยที่เข้าใจง่าย หลีกเลี่ยงแสดงชื่อ API, database หรือรหัส error ภายในแทนข้อความผู้ใช้

## 8. ชุด mock สำหรับตรวจ flow

ข้อมูลทั้งหมดเป็นข้อมูลสมมติ สนามและผู้เล่นไม่ใช่รายงานสถานการณ์จริง สร้างเวลาอิงวันทดสอบเพื่อไม่ให้ทุกนัดกลายเป็นอดีตเมื่อเปิดต้นแบบภายหลัง

| กรณี | ข้อมูลที่ต้องมี |
|---|---|
| 5x5 เปิดรับ | ผู้จัด 1 + เพื่อน 2 = 3/5 ขาด 2 คน เข้าได้เลย |
| 3x3 รออนุมัติ | ผู้จัด 1 + สมาชิก 1 = 2/3 ขาด 1 คน และมีคำขอรอที่ยังไม่นับ |
| นัดเต็ม | 5/5 คน ผู้ไม่ได้ร่วมเข้าต่อไม่ได้ สมาชิกเดิมยังแชทได้ |
| นัดปิดรับ | 3/5 คน แต่ผู้จัดหยุดรับ ไม่ควรแสดงปุ่มเข้าร่วม |
| นัดยกเลิก/จบแล้ว | แสดงในประวัติและไม่รับเพิ่ม |
| การเข้าร่วมชนกัน | จำลองคำตอบว่าที่นั่งเต็มหลังแตะเข้าร่วม โดยไม่เพิ่มสมาชิกสำเร็จ |

## 9. แนวทาง UI และลำดับทำงาน

- อิงมือถือและ stack ที่ทีมเสนอคือ React Native + Expo + TypeScript; ตรวจ source จริงก่อนตัดสินโครงสร้างไฟล์หรือไลบรารีเพิ่มเติม
- ใช้ component กลาง เช่น การ์ดนัด ป้ายสถานะ สรุปจำนวนคน ตัวเลือกระดับ/ตำแหน่ง ตัวกรอง และช่องสมาชิก
- เน้นสนาม เวลา และจำนวนที่ขาดให้เห็นเร็ว ปุ่มหลักต่อหน้าต้องชัด
- ใช้สีร่วมกับข้อความ ไม่สื่อระดับหรือสถานะด้วยสีอย่างเดียว
- ฟอร์มและแชทต้องเลื่อนใช้งานได้เมื่อคีย์บอร์ดเปิด รองรับข้อความไทยและจอเล็ก
- การเปิด GPS การรออนุมัติ และข้อมูลที่ยังไม่ทราบต้องมีทางไปต่อที่เข้าใจได้

**ลำดับที่เสนอ:** (1) ข้อมูล mock/component กลาง → (2) ฟีดและรายละเอียดนัด → (3) สร้างนัด/เข้าร่วม/ถอนตัว/คำขอ → (4) นัดของฉันและแชท → (5) สนาม โปรไฟล์ และสถานะผิดพลาด → (6) เชื่อมข้อมูลจริงตาม contract ที่ตรวจร่วมกัน

## 11. สิ่งที่ยังไม่รวมใน frontend รอบนี้

โพสต์โซเชียลทั่วไป ไลก์/คอมเมนต์ ติดตามก๊วนเต็มระบบ สถานะ “ฉันว่าง” การจับคู่และส่งแจ้งเตือนอัตโนมัติ รีวิว/รายงานสนามเต็มระบบ คะแนนความน่าเชื่อถือ ทัวร์นาเมนต์ การจองหรือชำระเงิน การแบ่งทีมอัตโนมัติ และคิวชนะอยู่ต่อของทั้งสนาม

ยังต้องยืนยันก่อนเชื่อมจริง: ช่องทางล็อกอิน, API/data contract, การส่งต่อผู้จัด, การแทนที่เพื่อนด้วยบัญชี, อายุและสิทธิ์แชท, การหมดอายุนัด, ผลของการบล็อก และบริการแผนที่ การแจ้งเตือนใช้ชุดเหตุการณ์จากงานหลักก่อน ได้แก่ ผลคำขอ สมาชิกเปลี่ยน สนาม/เวลาเปลี่ยน และยกเลิกนัด; ช่องทาง push จริงต้องตรวจร่วมกับ backend

## 12. ข้อความส่งต่อทีม

> ช่วยทำ frontend HoopUp ตาม brief นี้ โดยยึดแกน “เปิดนัดเล่นบาสแล้วให้คนมาเติมทีม” ใช้หน่วยนัดเดียวกันทั้งฟีด แผนที่ นัดของฉัน และแชท เริ่มด้วย mock data ให้ flow สร้างนัด–ค้นหา–เข้าร่วม–อนุมัติ–ถอนตัว–นัดพบทำงานครบ พร้อมสถานะโหลด/ว่าง/ผิดพลาด “เล่นตอนนี้” เป็นตัวเลือกเวลา ไม่แยกโหมด รายละเอียดที่ระบุว่า baseline/TBD ให้ตรวจร่วมกันก่อนเชื่อม backend จริง
